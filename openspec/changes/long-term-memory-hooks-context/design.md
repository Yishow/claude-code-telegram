## Context

目前系統主要依賴 provider session resume 維持上下文，並以「使用者 + 工作目錄」作為續聊邏輯。現有儲存層會保存原始問答與工具使用紀錄，但下次提問前不會主動把歷史萃取成可重用記憶並回灌。  
在目錄切換、長時間會話、或 provider 端壓縮後，關鍵決策與偏好可能難以穩定重現。此次變更要補齊「可控、可追溯、可回退」的長期記憶機制，且預設開啟 AI 增強層（`gpt-5-mini`），同時保留 deterministic 基礎層確保可用性。  
此外，AI 增強層需拆分為多個可獨立切換模組，並可在 Telegram 內即時調整，讓使用者可依當前任務自由切換記憶強化策略。

### Copilot SDK 深度分析結論
- SDK 目前提供的 runtime control 主要是 `reasoning_effort`、skills、MCP env mode、external server；未提供「記憶子模組」原生欄位。
- SDK hook 主要聚焦工具與錯誤處理（`on_pre_tool_use`、`on_error_occurred` 等），不包含應用層所需的「prompt 送出前/回覆後」記憶抽取介面。
- 既有持久化中，Copilot session map 僅保存 session 對應；Telegram `user_data` 目前未啟用框架持久化，無法保證重啟後維持。
- 因此本變更需在「應用層 + storage」實作記憶模組狀態與持久化，並把 Copilot SDK 當作增強模型執行通道，而非配置真實來源。

## Goals / Non-Goals

**Goals:**
- 建立前置（pre-send）與後置（post-response）記憶 hooks，形成可持續運作的記憶管線。
- 實作雙層記憶策略：deterministic 基礎層 + AI 增強層（預設開啟）。
- 將 AI 增強拆為可獨立開關模組（extractor、reranker、conflict_detector、periodic_review）。
- 提供 Telegram 內可自由切換的控制入口（狀態查詢、模組開關、預設組合）。
- 新增 `memory_system_plus` 總開關，確保未啟用時完全維持原邏輯。
- 確保增強層失敗時自動回退，不影響既有對話主流程。
- 為每次記憶召回與淘汰決策留下可觀測紀錄，支援除錯與審計。
- 維持專案目錄隔離，避免跨專案記憶污染。

**Non-Goals:**
- 不取代現有 provider session resume 機制。
- 不在本次引入複雜向量資料庫或跨租戶共享記憶。
- 不改變既有安全邊界（工具白名單、目錄邊界、權限流程）。
- 不承諾「零誤差還原」所有歷史細節。

## Decisions

### 1) 記憶資料模型採「原始紀錄 + 結構化記憶」雙軌
- 決策：保留既有原始訊息儲存，新增結構化記憶項目（事實、決策、待辦、偏好）與來源訊息關聯。
- 理由：可追溯、可修正，不會因摘要漂移失去原始依據。
- 替代方案：
  - 僅保存摘要文字：實作快，但漂移與不可追溯風險高。
  - 僅靠 provider session：無法跨 session 穩定延續重點。

### 2) Hook 插點設在「送出前」與「回覆後」
- 決策：送出 prompt 前執行 context assembly；回覆完成後執行 condensation 寫入記憶。
- 理由：不破壞現有 message -> run_command 主路徑，易於以 feature flag 漸進啟用。
- 替代方案：
  - 只做回覆後摘要：無法在下一輪即時利用。
  - 只做送出前拼接：沒有新記憶輸入，效果會快速衰退。

### 3) 增強層預設啟用，模型預設 `gpt-5-mini`
- 決策：AI 增強層預設開啟，用於抽取品質提升、記憶重排、衝突提示；失敗即回退 deterministic。
- 理由：在成本可接受前提下，提升記憶品質與檢索相關度；同時以回退保護穩定性。
- 替代方案：
  - 預設關閉增強層：風險最低，但品質提升有限。
  - 僅 AI 無基礎層：故障時會直接影響可用性，不可接受。

### 4) AI 增強層採子模組化開關
- 決策：將增強層拆為四個子模組：`extractor`、`reranker`、`conflict_detector`、`periodic_review`，可獨立開關。
- 理由：不同任務對品質/延遲需求不同，細粒度開關可降低不必要成本與延遲，並提升可控性。
- 替代方案：
  - 單一增強總開關：操作簡單，但無法針對場景微調。
  - 全自動策略無手動介面：易失控，使用者缺乏即時調整能力。

### 5) 記憶召回採「規則優先 + AI 重排」
- 決策：先以 deterministic 規則做候選集（目錄/類型/新鮮度/重要度），再由增強層做重排與壓縮。
- 理由：可預測、可測試，且保留 AI 帶來的語意排序增益。
- 替代方案：
  - 全 AI 檢索：黑箱程度高，除錯與審計困難。
  - 全規則檢索：穩定但語意相關性較弱。

### 6) Telegram 提供即時控制面
- 決策：新增 Telegram 指令與 inline keyboard，允許使用者在會話中查詢/切換 AI 記憶模組。
- 理由：降低切換成本，避免每次都改 `.env` 或重啟服務。
- 替代方案：
  - 僅後台環境變數：控制粒度粗，回應慢。
  - 僅管理員可改：不符合使用者「自由切換」需求。

### 7) `memory_system_plus` 兼容閘門
- 決策：新增 `memory_system_plus` 為總開關。關閉時禁止記憶 hooks 與增強模組介入，執行路徑必須等價於既有實作。
- 理由：以最小風險導入新系統，先保證原邏輯正確，再逐步擴大。
- 替代方案：
  - 直接全量啟用：上線風險高，回歸問題難定位。
  - 只用細部模組開關：缺少一鍵回退保險。

### 8) 模組設定以應用層儲存為單一真相
- 決策：AI 模組開關與 profile 設定存於 application storage，Copilot SDK runtime controls 僅在請求發送時映射成執行參數。
- 理由：避免把不受 SDK 支援的狀態誤放到 provider metadata，並確保重啟可恢復。
- 替代方案：
  - 只存在 `context.user_data`：重啟遺失，與需求衝突。
  - 直接寫入 SDK session metadata：目前介面不保證可用且耦合過深。

### 9) 可觀測性採結構化事件而非純文字日誌
- 決策：記錄召回命中、淘汰原因、估算 token、回退原因、增強層延遲與失敗率。
- 理由：支援後續 A/B 比較與品質調優。
- 替代方案：
  - 只記一般 log：缺乏可量化觀測維度。

## Risks / Trade-offs

- [摘要漂移導致錯誤記憶] -> 保留來源訊息 ID、支援人工標記失效、衝突時不覆蓋舊值。
- [增強層超時或失敗影響體驗] -> 設定嚴格 timeout，超時立即回退 deterministic 並記錄事件。
- [跨專案記憶污染] -> 召回必須以工作目錄為硬性過濾條件。
- [敏感資訊長期保存風險] -> 寫入前脫敏與欄位白名單，觀測資料不落敏感原文。
- [使用者頻繁切換造成狀態混亂] -> 提供目前生效配置查詢與切換審計紀錄，切換後即時回覆確認。
- [SDK/Provider 能力差異造成設定不一致] -> 採「應用層設定為準 + 發送前映射」策略，並在不支援時記錄降級事件。
- [記憶系統+ 導入造成原流程回歸] -> 建立 `memory_system_plus=off` 回歸測試基線，發生異常時一鍵回退。
- [系統複雜度上升] -> 以 feature flags 分段上線，先觀測再擴大。

## Migration Plan

1. 新增設定與 feature flags（`memory_system_plus`、記憶總開關、增強層開關、子模組開關、增強層預設模型、timeout、召回上限）。
2. 新增記憶儲存結構與 repository 介面，保留既有訊息儲存不變。
3. 實作 deterministic 基礎層（抽取/召回/拼接）並加入單元測試。
4. 實作 AI 增強層（預設 `gpt-5-mini`）與子模組化執行邏輯、故障回退機制。
5. 實作 Telegram 控制指令/按鈕與設定持久化。
6. 實作 `memory_system_plus` 閘門與原流程等價回歸驗證。
7. 實作「設定 -> SDK 執行參數」映射與降級處理。
8. 加入觀測事件與儀表資訊，驗證失敗率、延遲與切換行為。
9. 進行測試與效能優化迭代（召回準確率、延遲、回退率）。
10. 漸進啟用：先內部啟用、監看指標，再全面啟用。
11. 回滾策略：關閉 `memory_system_plus` 或僅關閉增強層/子模組，立即回到既有 session resume 行為。

## Open Questions

- 增強層 timeout 與重試次數的預設值要偏保守（延遲優先）還是偏品質（完整度優先）？
- 結構化記憶的 TTL 是否要依類型分級（例如決策比待辦保留更久）？
- 當使用者先套用 profile 再手動切換單一模組時，最終優先序與回報格式要如何定義？
